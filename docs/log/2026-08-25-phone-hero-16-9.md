# The phone hero is a 16:9 picture, with the copy below it
**Date:** 2026-08-25 · **Status:** REVERTED — wrong picture (never reached production)

## Goal — and the misread

Tina: *"on phone i want the picture on the hompage just to be 16:9"*.

**This was applied to the wrong picture and has been reverted.** She meant the
EDITORIAL cards at the foot of the homepage, not the hero: *"uh the hero is 16:9
i didnt want that i wanted the editorials on the end of the homepage to be that
or at least the most recent one"*.

The root error is §10.29, and it is worth naming precisely because a clarifying
question WAS asked and still did not catch it: the question asked *how* to make
the picture 16:9 once it broke — it never asked *which* picture "the picture on
the homepage" meant. The homepage has a hero, a category strip, two product
rails, three edit banners, a seal band, a map and an editorial section. "The
picture" was ambiguous across all of them and it was resolved by assumption.

Everything below is kept because the measurements are real and the finding —
that a 219px hero cannot hold that copy — stays true if 16:9 is ever wanted on
the hero deliberately.

## The literal version breaks, and that was measured before proposing anything

Applying `aspect-ratio: 16/9` to `.hero-vh` works geometrically — 390x219 at
1.778 — and destroys the hero, because the headline, subcopy and CTA are an
overlay INSIDE it. A full-screen hero gives that copy ~800px; 16:9 gives 219.

Measured at 390px, in WebKit, before showing her anything:

```
hero 390x219  (ratio 1.778, correct)
h1 overlaps the header by 19,681 px2   <- the headline runs through logo + burger
CTA lands on top of the subcopy
```

So the ask was put back to her with the evidence and three options. She chose
**"16:9 picture, text below it"**.

Worth recording that the FIRST probe said `contentOverflow: []` — it compared
child rects to the hero box, and absolutely-positioned children that overlap
each other and clip under `overflow: hidden` do not exceed that box. The
screenshot is what showed the truth (§10.22: an automated pass proves only what
it measures).

## What changed

**The copy became a SIBLING of the picture, not a child.**

```
<div className="relative">              <- new positioning wrapper
  <div data-hero className="... hero-vh">   picture, tints, HeroCallouts
  <div className="hero-copy ... lg:absolute lg:inset-0">  h1, p, desktop CTA
  <div className="... lg:hidden">          phone CTA
</div>
```

From `lg` up the copy is `absolute inset-0` over the picture — byte-for-byte the
old behaviour. Below `lg` it is static, so it flows underneath.

**Not duplicated markup with `lg:hidden` twins.** That was the obvious shortcut
and it would have put **two `<h1>`s** in the DOM. One copy block, two positioning
modes; `h1Count` is asserted at 1 at every width.

**`app/globals.css`:**
- `.hero-vh` gets `aspect-ratio: 16/9` under 1024px, with `height: auto` **and**
  `min-height: 0`. Both are required — the base rule sets a 560px floor, and an
  aspect-ratio cannot shrink a box below its own min-height, so leaving the floor
  in place makes the ratio silently do nothing, which looks exactly like the rule
  not applying.
- `.hero-copy` carries `--hero-fg` / `--hero-fg-dim` as vars, swapped in the same
  media query: white over the photograph, ink on parchment below it. A var
  because an inline style cannot be responsive and §6 says colour is never a
  Tailwind class — this is the only route that keeps both rules.
- 1024px, not this file's usual 820, because `--band-height`, the flat mobile
  hero tint and the copy block's own `lg:` alignment all already split there. A
  tablet getting a 16:9 photo with the text still floating on it would be the
  bug.

**The phone CTA** moved from `absolute bottom-16` to static, and inverted from
parchment-on-ink to **aubergine with parchment text** — a parchment pill is
invisible once it stops sitting on a darkened picture.

### The near-miss worth keeping

The phone CTA's inline style block is **byte-identical** to the desktop CTA's. A
replace on the style alone would have silently turned the desktop button
aubergine on a dark photograph too. The script asserted `count == 1`, threw, and
the edit was re-anchored on the wrapper instead. Python writes at the end, so
`page.tsx` was untouched by the failed run — worth knowing, because the same
mistake in a `sed` pipeline would have half-applied.

## The a11y violation this surfaced — NOT mine

`npm run audit:mobile` went `a11y 0` → `a11y 1` in both engines. I assumed it was
my subcopy and changed a colour on that assumption. **It was not.** Reading the
actual node from `.audit/report.json`:

```
<a class="btn-pill inline-block mt-8" style="background:var(--brass);color:var(--parchment)">
```

That is the homepage seal band's CTA. Parchment on brass measures **3.03:1** —
under AA's 4.5:1 for body text and barely over the 3.0 large-text floor.

Established rather than asserted (§10.38 rule 1: find out whether it ever
passed):
- my working tree touches **0** lines containing `btn-pill` or `--brass`
- the button last changed in `cedd781 style(home): gold pill with white letters
  on the seal band` — another session's commit
- `cedd781` landed **after** `ac90f38`, the last audit run that reported `a11y 0`

So it arrived with that commit and is already on staging. **Not fixed here** —
it is another session's live design iteration with Tina (purple pill → gold pill
in consecutive commits) and changing the colour would undo her choice. Flagged
to her instead.

**A correction I made to my own comment.** Having guessed wrong, I had written
into `globals.css` that `--muted` caused the audit to go 0 → 1. It did not. The
comment now says what is true: `--muted` measures 3.76:1, axe did **not** flag it
because the subcopy falls under the large-text threshold, and it was changed on
the measurement rather than on a failing check. `--ink` at 72% is 6.37:1.
